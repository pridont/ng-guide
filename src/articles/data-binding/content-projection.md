# Content Projection — `ng-content`

[`input()`](./input-output.html) მშობელს საშუალებას აძლევს, შვილს
**მონაცემი** გადასცეს. მაგრამ რა ვქნათ, თუ გადასაცემი მარკაპია?

წარმოიდგინეთ "ბარათის" კომპონენტი — ჩრდილითა და ჩარჩოს სტილით.
მისი შიგთავსი ყოველ ჯერზე სხვადასხვაა: ერთგან ტექსტი, მეორეგან სურათი,
მესამეგან სულ სხვა კომპონენტი. ამის `input()`-ით გადაცემა შეუძლებელია.

ამისთვის არსებობს `<ng-content>`:

```ts
@Component({
  selector: "app-card",
  template: `
    <div class="card-shadow">
      <ng-content />
    </div>
  `,
})
export class Card {}
```

გამოყენება:

```html
<app-card>
  <p>This is the projected content</p>
</app-card>
```

დარენდერებული DOM:

```html
<app-card>
  <div class="card-shadow">
    <p>This is the projected content</p>
  </div>
</app-card>
```

ანუ ის, რაც კომპონენტის თეგებს შორის ჩავწერეთ, გადავიდა (**projected**)
იმ ადგილას, სადაც `<ng-content>` იდგა.

ამ მექანიზმს ბრაუზერის სტანდარტულ [`<slot>` ელემენტთან](https://developer.mozilla.org/docs/Web/HTML/Element/slot)
აქვს მსგავსება.

## View და Content

აქ ორი ტერმინი ჩნდება, რომელთა გარჩევაც მნიშვნელოვანია:

- **view** — ის ელემენტები, რომლებიც კომპონენტის **საკუთარ** თემფლეითშია
  აღწერილი
- **content** — ის ელემენტები, რომლებიც კომპონენტს **გარედან** გადმოეცა

სწორედ ამიტომ არსებობს [query ფუნქციების](./queries.html) ორი ჯგუფი:
`viewChild` პირველში ეძებს, `contentChild` — მეორეში.

## `<ng-content>` არ არის ელემენტი

`<ng-content>` არც კომპონენტია და არც DOM ელემენტი — ის უბრალოდ
ნიშნულია, რომელიც ანგულარს ეუბნება, სად ჩასვას შიგთავსი. ქომფაილერი მას
**ბილდის დროს** ამუშავებს.

აქედან ორი შეზღუდვა გამომდინარეობს:

- მასზე დირექტივების, სტილების ან ატრიბუტების დადება არ შეიძლება
- გაშვების დროს მისი დამატება, წაშლა ან შეცვლა შეუძლებელია

**მნიშვნელოვანია:** `<ng-content>` ანგულარის [control flow-ში](/control-flow/index.html), ანუ
`@if`-ში, `@for`-სა ან `@switch`-ში
არ უნდა მოვათავსოთ. ანგულარი პროექტირებულ შიგთავსს **ყოველთვის ქმნის**,
მაშინაც კი, თუ `<ng-content>` დამალულია. შიგთავსის პირობითი რენდერისთვის
`ng-template` გამოიყენება.

## რამდენიმე სლოტი

ხშირად კომპონენტს რამდენიმე ადგილას სჭირდება შიგთავსი, მაგალითად,
ბარათს სათაური და სხეული აქვს. ამისთვის `select` გამოიყენება:

```ts
@Component({
  selector: "app-card-title",
  template: `<ng-content />`,
})
export class CardTitle {}

@Component({
  selector: "app-card-body",
  template: `<ng-content />`,
})
export class CardBody {}

@Component({
  selector: "app-card",
  template: `
    <div class="card-shadow">
      <ng-content select="app-card-title" />
      <div class="card-divider"></div>
      <ng-content select="app-card-body" />
    </div>
  `,
})
export class Card {}
```

გამოყენება:

```html
<app-card>
  <app-card-title>Hello</app-card-title>
  <app-card-body>Welcome to the example</app-card-body>
</app-card>
```

`select` CSS სელექტორს იღებს, ამიტომ კომპონენტის ნაცვლად კლასზეც
შეგვიძლია მითითება: `<ng-content select=".title" />`.

`select`-ის გარეშე დარჩენილი `<ng-content>` ყველა იმ შიგთავსს იჭერს,
რომელიც სხვა სლოტს არ მოერგო.

## ნაგულისხმევი შიგთავსი

თუ მომხმარებელმა რომელიმე სლოტს არაფერი მიაწოდა, შეგვიძლია ნაგულისხმევი
შიგთავსი ვაჩვენოთ — ის უბრალოდ `<ng-content>`-ის შიგნით იწერება:

```html
<div class="card-shadow">
  <ng-content select="app-card-title">Default Title</ng-content>
  <div class="card-divider"></div>
  <ng-content select="app-card-body">Default Body</ng-content>
</div>
```

თუ `app-card-body` არ გადმოეცა, მის ადგილას `Default Body` გამოჩნდება.

## `ngProjectAs` — სხვა სახელით ჩაწერა

ზოგჯერ სლოტში ჩვეულებრივი HTML ელემენტის ჩასმა გვინდა, და არა
სპეციალური კომპონენტის. ამისთვის `ngProjectAs` ატრიბუტია — ის ანგულარს
ეუბნება, რომ ეს ელემენტი კონკრეტულ სელექტორად ჩათვალოს:

```html
<app-card>
  <h3 ngProjectAs="app-card-title">Hello</h3>
  <p>Welcome to the example</p>
</app-card>
```

`h3` მოხვდება სათაურის სლოტში, თუმცა თვითონ `app-card-title` კომპონენტი
არ არის. `p` კი დარჩენილ `<ng-content>`-ში ჩავარდება.

`ngProjectAs` მხოლოდ სტატიკურ მნიშვნელობებთან მუშაობს — მისი ბაინდინგი
შეუძლებელია.

## გასათვალისწინებელი

### პროექტირებული შიგთავსი მშობელს ეკუთვნის

მიუხედავად იმისა, რომ შიგთავსი **რენდერდება** მიმღები კომპონენტის შიგნით,
ის კვლავ იმ კომპონენტს ეკუთვნის, რომელმაც ის **დაწერა**. ანგულარი მას
მშობლის view-ის ნაწილად აღიქვამს.

აქედან ორი შედეგი გამომდინარეობს:

**Change detection.** პროექტირებული შიგთავსი მაშინ მოწმდება, როცა
**მშობელი** მოწმდება. თუ მიმღები კომპონენტი `OnPush`-ია, ანგულარმა
შეიძლება მისი საკუთარი თემფლეითი გამოტოვოს — მაგრამ პროექტირებულ
შიგთავსს ვერ გამოტოვებს, რადგან ის მშობლისაა:

```html
<!-- მშობლის თემფლეითი -->
<app-onpush-wrapper>
  <!-- ეს მაინც შემოწმდება მშობლის ყოველ ციკლზე -->
  <app-expensive-component />
</app-onpush-wrapper>
```

[Dependency injection-ის](/dependency-injection/index.html) დროს პროექტირებული შიგთავსი დამოკიდებულებებს
**მშობლის** ინჯექტორიდან იღებს, და არა მიმღები კომპონენტისგან.

## შეჯამება

- `<ng-content>` კომპონენტს საშუალებას აძლევს, მარკაპი გარედან მიიღოს
- `select` ატრიბუტით რამდენიმე სლოტის შექმნა შეიძლება
- `<ng-content>`-ის შიგნით ჩაწერილი შიგთავსი ნაგულისხმევია
- `ngProjectAs`-ით ჩვეულებრივ ელემენტს სლოტში ვამისამართებთ
- პროექტირებული შიგთავსი მშობელს ეკუთვნის — როგორც change detection-ის,
  ისე DI-ის თვალსაზრისით

`<ng-content>` სწორედ ის მექანიზმია, რომელიც ხელახლა გამოსაყენებელი
"გარსისებრი" კომპონენტების (ბარათები, მოდალები, ღილაკები, აკორდეონები)
შექმნის საშუალებას იძლევა.

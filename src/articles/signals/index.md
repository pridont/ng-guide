# რა არის სიგნალები?

**Angular Signals** არის სისტემა, რომელიც თვალს ადევნებს სად არის
ჩვენი აპლიკაციის სთეითი და როგორ იცვლება ის. შედეგად ანგულარი
ოპტიმიზირებულად არენდერებს თემფლეითებს.

**სიგნალი** არის ერთგვარი მნიშვნელობის შემფუთველი, რომელიც აცნობებს
დაინტერესებულ კონსუმერებს, როდის იცვლება ეს მნიშვნელობა. სიგნალებში შესაძლებელია
ნებისმიერი მნიშვნელობის შენახვა, მარტივი პრიმიტივებიდან კომპლექსური მონაცემის სტრუქტურებამდე.

სიგნალები დღეს ანგულარის ბირთვია. მათზეა აშენებული
[`input()` და `output()`](/data-binding/input-output.html), ფორმები,
მონაცემების ჩამოტვირთვა და თემფლეითების განახლების მექანიზმი. სწორედ
ამიტომ ღირს ამ თავის კარგად გაგება.

## Writable Signals

მოდიფიცირებადი სიგნალები გვაწვდიან API-ს მათი მნიშვნელობების გასაახლებლად.
სიგნალები იქმნება `signal` ფუნქციით (`@angular/core`-დან), რომელსაც საწყისი მნიშვნელობა უნდა მივაწოდოთ.

```ts
count = signal(0);
```

ასეთი სიგნალის ტიპი არის `WritableSignal<number>` — ტიპი საწყისი
მნიშვნელობიდან გამოიცნობა.

თემფლეითში ამ მნიშვნელობის გამოსატანად ჩვენ `count`-ს ფუნქციასავით ვეძახით:

```html
<button>Count: {{ count() }}</button>
```

სიგნალის მნიშვნელობის შესაცვლელად შეგვიძლია მასზე `set` მეთოდს დავუძახოთ:

```html
<button (click)="count.set(3)">Count: {{ count() }}</button>
```

თუ მნიშვნელობის განახლება გვინდა, მაგრამ ამისთვის სიგნალის წინა მნიშვნელობა გვჭირდება,
მაშინ `update` მეთოდი გამოგვადგება, სადაც ქოლბექში წინა მნიშვნელობას ვიღებთ და შეგვიძლია
ახალი დავაბრუნოთ:

```ts
count.update((value) => value + 1);
```

### მხოლოდ წასაკითხი სიგნალი

ხშირად გვინდა, რომ სერვისმა სთეითი გარეთ **წასაკითხად** გამოიტანოს, მაგრამ
მისი შეცვლა მხოლოდ თვითონ შეძლოს. ამისთვის `WritableSignal`-ს აქვს
`asReadonly()` მეთოდი:

```ts
import { Service, signal } from "@angular/core";

@Service()
export class CounterState {
  // შიდა, მოდიფიცირებადი სთეითი
  private readonly _count = signal(0);

  // გარეთ გამოტანილი, მხოლოდ წასაკითხი
  readonly count = this._count.asReadonly();

  increment() {
    this._count.update((value) => value + 1);
  }
}
```

კომპონენტს ახლა `count`-ის კითხვა შეუძლია, მაგრამ `set`/`update` მეთოდები
მასზე არ არსებობს — სთეითის შეცვლა მხოლოდ `increment()`-ითაა შესაძლებელი.

**გაითვალისწინეთ:** `asReadonly()` მხოლოდ სიგნალის *ჩანაცვლებას* კრძალავს.
თუ სიგნალში ობიექტი ან მასივი გვაქვს, მისი შიგთავსის მუტაციას ის ვერ
შეაჩერებს.

## Computed Signals

გამოთვლილი სიგნალები არიან არამოდიფიცირებადი სიგნალები, რომლებიც მნიშვნელობას
სხვა სიგნალებიდან გამომდინარე ატარებენ:

```ts
@Component({
  template: `
    <button (click)="increment()">Count: {{ count() }}</button>
    <p>Is even: {{ isCountEven() }}</p>
  `,
})
export class App {
  count = signal(0);
  isCountEven = computed(() => this.count() % 2 === 0);

  increment() {
    this.count.update((value) => value + 1);
  }
}
```

ამ მაგალითში `isCountEven` ეყრდნობა `count` სიგნალს.
`count`-ის მნიშვნელობის შეცვლასთან ერთად სათანადოდ შეიცვლება `isCountEven`.

გასათვალისწინებელია, რომ გამოთვლილი სიგნალი _არ არის მოდიფიცირებადი_ —
`Signal` ტიპზე არ არსებობს `set` და `update` მეთოდები.

გამოთვლილი სიგნალები **ზარმაცად** მუშაობენ. ისინი იმ შემთხვევაში აწარმოებენ
კალკულაციას, თუ სიგნალი, რომელზეც ისინი ეყრდნობიან, შეიცვალა. სხვა შემთხვევაში
ხდება პირვანდელი გამოთვლილი მნიშვნელობის ქეშირება და, სიგნალზე დაძახების შემთხვევაში,
ამ ქეშის აღდგენა.

### დამოკიდებულებები დინამიურია

`computed`-ის დამოკიდებულებები **წინასწარ არ არის დაფიქსირებული** — ისინი
ყოველ გამოთვლაზე ხელახლა განისაზღვრება, იმის მიხედვით, რომელი სიგნალი
იყო რეალურად წაკითხული:

```ts
showCount = signal(false);
count = signal(0);

label = computed(() => {
  if (this.showCount()) {
    return `Count: ${this.count()}`;
  }
  return "Nothing to see here!";
});
```

სანამ `showCount` არის `false`, `label` **არ არის დამოკიდებული** `count`-ზე —
`count`-ის შეცვლა `label`-ს ხელახლა არ გამოთვლის. როგორც კი `showCount`
გახდება `true`, `count` დამოკიდებულებად დაემატება.

## Reactive Context

სიგნალები ჯადოსნურად არ იცნობენ ერთმანეთს. `computed` და `effect`
დამოკიდებულებებს **იმის მიხედვით ადგენს, რომელი სიგნალი წაიკითხა მათი
ფუნქციის შესრულებისას**. სწორედ ამ ფუნქციის შესრულების პერიოდს ჰქვია
reactive context.

ეს ორი მნიშვნელოვან შედეგს იძლევა.

### `untracked` — კითხვა თვალის დევნების გარეშე

ზოგჯერ reactive context-ში სიგნალის წაკითხვა გვინდა, მაგრამ არ გვინდა,
რომ ის დამოკიდებულებად ჩაითვალოს. ამისთვის არსებობს `untracked`:

```ts
effect(() => {
  // ეს ეფექტი მხოლოდ currentUser-ის ცვლილებაზე გაეშვება,
  // counter-ის ცვლილებაზე — არა
  console.log(`User: ${this.currentUser()}, counter: ${untracked(this.counter)}`);
});
```

`untracked` მაშინაც გამოგვადგება, როცა ეფექტიდან გარე კოდს ვიძახებთ და
არ ვიცით, ის შიგნით რომელ სიგნალებს კითხულობს:

```ts
effect(() => {
  const user = this.currentUser();
  untracked(() => {
    // თუ loggingService სიგნალებს კითხულობს, ისინი ამ ეფექტის
    // დამოკიდებულებებად არ ჩაითვლება
    this.loggingService.log(`User set to ${user}`);
  });
});
```

### `await`-ის შემდეგ context იკარგება

reactive context **მხოლოდ სინქრონული კოდისთვის** არის აქტიური. ყველა
სიგნალი, რომელსაც `await`-ის შემდეგ წავიკითხავთ, დამოკიდებულებად **არ**
ჩაითვლება:

```ts
// არასწორია
effect(async () => {
  const data = await fetchUserData();
  // context უკვე დაკარგულია — theme() თვალის დევნებაში არ ხვდება
  console.log(`User: ${data.name}, Theme: ${this.theme()}`);
});
```

გამოსავალი: სიგნალები `await`-ამდე წავიკითხოთ.

```ts
// სწორია
effect(async () => {
  const currentTheme = this.theme(); // წაკითხვა await-ამდე
  const data = await fetchUserData();
  console.log(`User: ${data.name}, Theme: ${currentTheme}`);
});
```

ეს ერთ-ერთი ყველაზე ხშირი შეცდომაა სიგნალებთან მუშაობისას.

## Effects

თუ სიგნალები ხელსაყრელია, რადგან ისინი დაინტერესებულ კონსუმერებს აცნობებენ ცვლილებებს,
ეფექტები გამოსადეგია მაშინ, როცა ჩვენ ერთი ან მეტი სიგნალის ცვლილებაზე გვინდა ისე ვირეაგიროთ,
რომ აპლიკაციის სთეითი **არ შეიცვალოს** (გამოთვლილი სიგნალებისგან განსხვავებით).

```ts
export class App {
  count = signal(0);

  constructor() {
    effect(() => {
      console.log(`The count was updated to ${this.count()}`);
    });
  }
}
```

აქ ჩვენ ეფექტს ვქმნით, რომელიც გაეშვება, როცა `count` სიგნალი მნიშვნელობას შეიცვლის.
ეფექტები ყოველთვის ეშვება **მინიმუმ ერთხელ**. როცა ეფექტი ეშვება, ის თვალყურს ადევნებს
ყველა მისთვის საჭირო სიგნალს და ყოველ ცვლილებაზე ხელახლა ეშვება.

ეფექტები ფუნქციონირებას წყვეტენ, როცა კომპონენტი ნადგურდება.

### სად ვქმნით ეფექტს

`effect()`-ის დაძახება მხოლოდ **injection context**-ში შეიძლება — ანუ
კონსტრუქტორში ან კლასის თვისების ინიციალიზაციაში. სხვა ადგილას
(მაგალითად რომელიმე მეთოდში) მისი შექმნა ერორს გამოიწვევს, თუ
`Injector`-ს ჩვენით არ მივაწოდებთ.

### როდის გამოვიყენოთ

ეფექტები **გამონაკლისია, არა წესი**. მათი ტიპური გამოყენების შემთხვევებია:

- ლოგირება
- მონაცემების `localStorage`-ში სინქრონიზაცია
- გარე, არარეაქტიული ბიბლიოთეკის გამოძახება (მაგ. სქემების ან რუკის ბიბლიოთეკა)
- DOM-ის ხელით მანიპულაცია

**რისთვის _არ_ გამოვიყენოთ:** ერთი სიგნალიდან მეორის გამოთვლისთვის.
ეს `computed`-ის (ან `linkedSignal`-ის) საქმეა. `effect`-ში სთეითის
შეცვლა კოდს ძნელად სამართავს ხდის და უსასრულო ციკლს იწვევს.

### მოსუფთავება — `onCleanup`

ეფექტმა შეიძლება ხანგრძლივი ოპერაცია დაიწყოს (ტაიმერი, სუბსქრიფშენი,
მოთხოვნა). თუ ეფექტი ხელახლა გაეშვება ან განადგურდება, ეს ოპერაცია
უნდა გავაუქმოთ. ეფექტის ფუნქცია პირველ პარამეტრად `onCleanup` ფუნქციას
იღებს:

```ts
effect((onCleanup) => {
  const user = this.currentUser();

  const timer = setTimeout(() => {
    console.log(`1 second ago, the user became ${user}`);
  }, 1000);

  onCleanup(() => {
    clearTimeout(timer);
  });
});
```

`onCleanup`-ში დარეგისტრირებული ქოლბექი გაეშვება ეფექტის შემდეგი
გაშვების **წინ**, ან მაშინ, როცა ეფექტი განადგურდება.

### `afterRenderEffect` — DOM-თან მუშაობა

`effect` ეშვება **მანამ**, სანამ ანგულარი DOM-ს განაახლებს. თუ DOM-ის
ხელით შემოწმება ან მოდიფიკაცია გვჭირდება (ან ისეთი ბიბლიოთეკა, რომელსაც
რეალურ DOM ელემენტზე წვდომა სჭირდება), მაშინ `afterRenderEffect`-ს
ვიყენებთ. ის იგივენაირად მუშაობს, მაგრამ რენდერის დასრულების შემდეგ ეშვება.

## `linkedSignal` — დამოკიდებული სთეითი

ვთქვათ, გვაქვს კომპონენტი, სადაც მომხმარებელი ამანათის მიწოდების მეთოდს ირჩევს:

```ts
export class ShippingMethodPicker {
  shippingOptions = signal(["Ground", "Air", "Sea"]);

  // ნაგულისხმევად პირველი ვარიანტი
  selectedOption = signal(this.shippingOptions()[0]);
}
```

პრობლემა: `shippingOptions` სიგნალია — მისი მნიშვნელობა შეიძლება შეიცვალოს.
თუ ვარიანტების სია შეიცვლება, `selectedOption`-ში შეიძლება ისეთი მნიშვნელობა
დარჩეს, რომელიც სიაში აღარ არსებობს.

`computed` აქ ვერ გვიშველის, რადგან `selectedOption` მომხმარებელმაც უნდა
შეცვალოს. სწორედ ამისთვის არსებობს `linkedSignal`:

```ts
import { linkedSignal, signal } from "@angular/core";

export class ShippingMethodPicker {
  shippingOptions = signal(["Ground", "Air", "Sea"]);

  selectedOption = linkedSignal(() => this.shippingOptions()[0]);

  changeShipping(index: number) {
    this.selectedOption.set(this.shippingOptions()[index]);
  }
}
```

`linkedSignal` `signal`-ის მსგავსად მუშაობს, ერთი განსხვავებით: საწყისი
მნიშვნელობის ნაცვლად მას **გამოთვლის ფუნქციას** ვაწვდით, როგორც
`computed`-ს. როცა ამ გამოთვლის შედეგი შეიცვლება, `linkedSignal`-ის
მნიშვნელობა თავიდან დაუბრუნდება ამ შედეგს:

```ts
const shippingOptions = signal(["Ground", "Air", "Sea"]);
const selectedOption = linkedSignal(() => shippingOptions()[0]);
console.log(selectedOption()); // 'Ground'

selectedOption.set(shippingOptions()[2]);
console.log(selectedOption()); // 'Sea'

shippingOptions.set(["Email", "Will Call", "Postal service"]);
console.log(selectedOption()); // 'Email' — თავიდან დაბრუნდა
```

ერთი წინადადებით, როგორ გავაკეთოთ არჩევანი სამ ხელსაწყოს შორის:

- `signal` — დამოუკიდებელი სთეითი
- `computed` — სხვა სთეითიდან გამოთვლილი, მხოლოდ წასაკითხი
- `linkedSignal` — სხვა სთეითზე დამოკიდებული, მაგრამ მოდიფიცირებადი

## `resource` — ასინქრონული მონაცემები

ყველა აქამდე განხილული API სინქრონულია. აპლიკაციებს კი ხშირად სერვერიდან
ჩამოტვირთული მონაცემები სჭირდებათ. `resource` საშუალებას გვაძლევს,
ასინქრონული მონაცემი სიგნალების სამყაროში შემოვიტანოთ:

```ts
import { resource, signal } from "@angular/core";

userId = signal("1");

userResource = resource({
  // რეაქტიული გამოთვლა — იცვლება, როცა userId იცვლება
  params: () => ({ id: this.userId() }),

  // ასინქრონული ლოადერი, რომელიც ყოველ ახალ params-ზე გაეშვება
  loader: ({ params }) => fetchUser(params.id),
});
```

`resource` გვაძლევს რამდენიმე სიგნალს:

- `value()` — ჩამოტვირთული მნიშვნელობა
- `hasValue()` — არსებობს თუ არა მნიშვნელობა (ტაიპსკრიპტისთვის type guard-იც არის)
- `isLoading()` — მიმდინარეობს თუ არა ჩამოტვირთვა
- `error()` — ერორი, თუ მოხდა
- `status()` — დეტალური სტატუსი

```ts
firstName = computed(() => {
  if (this.userResource.hasValue()) {
    return this.userResource.value().firstName;
  }
  return undefined;
});
```

მოთხოვნის ხელახლა გასაშვებად არსებობს `reload()` მეთოდი.

HTTP მოთხოვნებისთვის ანგულარს აქვს უფრო სპეციალიზებული `httpResource`,
რომელსაც [HTTP-ის თავში](/http/) განვიხილავთ.

## RxJS-თან თავსებადობა

სიგნალები [RxJS](/rxjs/)-ს არ ცვლის — ისინი სხვადასხვა ამოცანას ხსნიან.
სიგნალი ყოველთვის *ერთ მიმდინარე მნიშვნელობას* ატარებს, ხოლო observable
*მნიშვნელობათა ნაკადს*. მათ შორის ხიდი `@angular/core/rxjs-interop`
პაკეტშია.

`toSignal` — observable-იდან სიგნალი:

```ts
import { toSignal } from "@angular/core/rxjs-interop";
import { interval } from "rxjs";

export class Ticker {
  counterObservable = interval(1000);
  counter = toSignal(this.counterObservable, { initialValue: 0 });
}
```

```html
<p>{{ counter() }}</p>
```

`toSignal` `async` ფაიფის მსგავსად მუშაობს, ოღონდ ის თემფლეითის გარეთაც
გამოიყენება. ის ავტომატურად აკეთებს `unsubscribe`-ს, როცა კომპონენტი ან
სერვისი, სადაც ის შეიქმნა, ნადგურდება.

`initialValue`-ის მითითება საჭიროა იმიტომ, რომ observable შეიძლება
მაშინვე არ დააემითოს მნიშვნელობა, სიგნალს კი ყოველთვის სჭირდება
მიმდინარე მნიშვნელობა. თუ `initialValue`-ს არ მივუთითებთ, სიგნალი
`undefined`-ს დააბრუნებს, სანამ observable არ გასცემს. `BehaviorSubject`-ის
მსგავს სტრიმებზე, რომლებიც აუცილებლად სინქრონულად გასცემენ მნიშვნელობას,
შეგვიძლია `requireSync: true` მივუთითოთ და მაშინ `undefined` ტიპში არ
გამოჩნდება.

`toObservable` — სიგნალიდან observable:

```ts
import { toObservable } from "@angular/core/rxjs-interop";

query = signal("");
query$ = toObservable(this.query);
```

ეს მაშინ გამოგვადგება, როცა სიგნალის ცვლილებებზე RxJS-ის ოპერატორების
გამოყენება გვინდა (მაგალითად `debounceTime` საძიებო ველისთვის).

## შედარების ფუნქცია

ნაგულისხმევად სიგნალი მნიშვნელობებს `Object.is`-ით ადარებს. ეს იმას
ნიშნავს, რომ ობიექტის ან მასივის შემთხვევაში **რეფერენსი** დგინდება, და
არა შიგთავსი:

```ts
data = signal({ name: "Tariel" });

// ეს ცვლილებად ჩაითვლება, თუმცა შიგთავსი იგივეა
data.set({ name: "Tariel" });
```

თუ სხვა ლოგიკა გვჭირდება, `equal` ოპციას ვაწვდით:

```ts
data = signal(
  { name: "Tariel" },
  { equal: (a, b) => a.name === b.name }
);
```

## შეჯამება

- `signal()` — მოდიფიცირებადი სთეითი. `set`/`update` მეთოდები, `asReadonly()`
  გარეთ გამოსატანად
- `computed()` — სხვა სიგნალებიდან გამოთვლილი, ზარმაცი, ქეშირებული,
  დინამიური დამოკიდებულებებით
- reactive context — `computed`/`effect` დამოკიდებულებებს კითხვის მიხედვით
  ადგენს. `untracked()` გამორიცხავს სიგნალს, `await` კი context-ს კლავს
- `effect()` — გვერდითი მოვლენებისთვის, არა სთეითის გამოსათვლელად.
  `onCleanup`-ით ვასუფთავებთ
- `linkedSignal()` — მოდიფიცირებადი, მაგრამ სხვა სთეითზე დამოკიდებული
- `resource()` — ასინქრონული მონაცემები სიგნალურ ფორმაში
- `toSignal`/`toObservable` — ხიდი RxJS-თან

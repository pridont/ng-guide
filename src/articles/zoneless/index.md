# Zoneless — zone.js-ის გარეშე

აქამდე ერთ კითხვას თავს ვარიდებდით: **ანგულარმა საიდან იცის, რომ რაღაც
შეიცვალა და თემფლეითი უნდა გადაარენდეროს?**

```ts
export class App {
  count = 0;

  increment() {
    this.count++; // ეს უბრალო ჯავასკრიპტია. ვინ ეუბნება ანგულარს?
  }
}
```

## როგორ მუშაობდა ეს zone.js-ით

მე-20 ვერსიამდე პასუხი იყო **zone.js** — ბიბლიოთეკა, რომელიც ბრაუზერის
API-ებს "პაჩავდა". ის ჩაენაცვლებოდა `setTimeout`-ს, `addEventListener`-ს,
`Promise`-ს, `XMLHttpRequest`-სა და ათეულობით სხვა ფუნქციას, რომ გაეგო,
როდის სრულდება ასინქრონული ოპერაცია.

ლოგიკა მარტივი იყო: თუ რაიმე ასინქრონული დასრულდა, ალბათ სთეითიც შეიცვალა,
ესეიგი ჯობია ყველაფერი შევამოწმოთ.

ეს მიდგომა მუშაობდა, თუმცა სამი პრობლემა გააჩნდა:

1. **ზედმეტი სამუშაო.** zone.js-მა არ იცოდა, რა შეიცვალა და შეიცვალა თუ
   არა საერთოდ. ის უბრალოდ _ეჭვობდა_ და მთელ აპლიკაციას ამოწმებდა.
2. **ბანდლის ზომა და გაშვების დრო.** zone.js თვითონ იყო დამატებითი კოდი,
   რომელიც ყოველ ჯერზე უნდა ჩამოტვირთულიყო და გაშვებულიყო.
3. **გაუგებარი სტეკ-ტრეისები და თავსებადობა.** დებაგინგი რთულდებოდა.
   ზოგიერთი თანამედროვე API კი (მაგალითად `async`/`await`) საერთოდ ვერ
   პაჩდებოდა და კომპილაციისას ძველ სინტაქსზე უნდა გადაკეთებულიყო.

## რა შეიცვალა

ანგულარის 21-ე ვერსიიდან **zoneless ნაგულისხმევი რეჟიმია**. ახალ პროექტში
`zone.js` საერთოდ არ არის დამოკიდებულებებში — შეგიძლიათ `package.json`-ს
შეხედოთ და დარწმუნდეთ.

ახლა ანგულარი აღარ ეჭვობს — მას **პირდაპირ ატყობინებენ**. შეტყობინების
წყაროებია:

- **სიგნალის შეცვლა**, რომელიც თემფლეითში იკითხება
- თემფლეითში ან `host`-ში მიბმული ივენთ ჰენდლერები
- `async` ფაიფი
- `ComponentRef.setInput`
- `ChangeDetectorRef.markForCheck`

სწორედ ამიტომ იყო ამ წიგნში სიგნალებზე ამდენი საუბარი: **სიგნალი მხოლოდ
მნიშვნელობის შესანახი ჭურჭელი არ არის — ის ამავე დროს ანგულარის
შეტყობინების მექანიზმია.**

## რას ნიშნავს ეს პრაქტიკაში

თუ ამ წიგნის კოდს მიჰყვებოდით, თქვენი აპლიკაცია უკვე zoneless-თავსებადია.
სიგნალები, `input()`, `output()`, `httpResource` — ყველა მათგანი
ანგულარს სათანადოდ ატყობინებს.

პრობლემა მაშინ ჩნდება, როცა სთეითს **ჩვეულებრივი თვისებით** ვმართავთ
და მას ისეთი ადგილიდან ვცვლით, რომელიც ანგულარს არ სცნობს:

```ts
// ❌ zoneless-ში თემფლეითი შეიძლება არ განახლდეს
export class App {
  count = 0;

  ngOnInit() {
    setTimeout(() => {
      this.count = 5; // ანგულარმა ამის შესახებ არაფერი იცის
    }, 1000);
  }
}
```

```ts
// ✅ სიგნალი ანგულარს თვითონ ატყობინებს
export class App {
  count = signal(0);

  ngOnInit() {
    setTimeout(() => {
      this.count.set(5);
    }, 1000);
  }
}
```

**წესი მარტივია: ის სთეითი, რომელიც თემფლეითში იკითხება, სიგნალში უნდა იყოს.**

ივენთ ჰენდლერები გამონაკლისია — მათ ანგულარი მაინც ამჩნევს:

```ts
// ეს იმუშავებს, რადგან (click) ჰენდლერს ანგულარი აკონტროლებს
increment() {
  this.count++;
}
```

მაგრამ მასზე დაყრდნობა არ ღირს — სიგნალი ყოველთვის უსაფრთხო არჩევანია.

## `OnPush`

zoneless-თან ერთად `ChangeDetectionStrategy.OnPush` **ნაგულისხმევი
სტრატეგია** გახდა (22-ე ვერსიიდან). მისი ხელით ჩაწერა აღარ არის საჭირო.

ძველ კოდში ის თითქმის ყველგან წერია, რადგან zone.js-ის დროს ეს იყო
ერთადერთი გზა, ანგულარისთვის ზედმეტი შემოწმებები აგვერიდებინა.

## ძველი პროექტის გადაყვანა

თუ 20-ე ან უფრო ძველ ვერსიაზე ხართ, zoneless რეჟიმი ხელით უნდა ჩართოთ:

```ts
bootstrapApplication(App, {
  providers: [provideZonelessChangeDetection()],
});
```

შემდეგ `zone.js` ბანდლიდან უნდა ამოვიღოთ. ის `angular.json`-ში
`polyfills` ველშია მითითებული — როგორც `build`, ისე `test` კონფიგურაციაში:

```sh
npm uninstall zone.js
```

### რას უნდა მივაქციოთ ყურადღება

- **`NgZone.onStable`, `NgZone.onMicrotaskEmpty`, `NgZone.onUnstable`** —
  zoneless რეჟიმში ეს observable-ები **არასდროს დააემითებენ**, ხოლო
  `NgZone.isStable` ყოველთვის `true` იქნება. თუ კოდი მათ ელოდება,
  ის სამუდამოდ გაიჭედება.

  სანაცვლოდ `afterNextRender` (ერთი რენდერისთვის) ან `afterEveryRender`
  გამოიყენება. თუ DOM-ის კონკრეტულ მდგომარეობას ველოდებით, ხშირად
  `MutationObserver` უფრო პირდაპირი გამოსავალია.

- **`NgZone.run` და `NgZone.runOutsideAngular` კი თავსებადია** და მათი
  წაშლა არ გვჭირდება. მეტიც, ბიბლიოთეკებში მათი წაშლა ზიანის მომტანია —
  ისინი კვლავ სჭირდებათ იმ აპლიკაციებს, რომლებიც zone.js-ს იყენებენ.

- **SSR-ის დროს `PendingTasks`.** სერვერზე რენდერისას ანგულარმა უნდა
  იცოდეს, როდის შეიძლება გვერდის სერიალიზება. zone.js-ის გარეშე მას ჩვენ
  უნდა ვაცნობოთ, თუ რაიმე ასინქრონული ოპერაცია მიმდინარეობს:

  ```ts
  const taskService = inject(PendingTasks);

  taskService.run(async () => {
    const result = await doSomeWork();
    this.someState.set(result);
  });
  ```

  `HttpClient`-ის მოთხოვნებზე ამის გაკეთება არ გვჭირდება — ანგულარი მათ
  თვითონ ითვალისწინებს.

## შეჯამება

zone.js ანგულარს ეუბნებოდა "რაღაც მოხდა, ყველაფერი შეამოწმე". სიგნალები
ეუბნებიან "ეს კონკრეტული მნიშვნელობა შეიცვალა". შედეგად ანგულარი ნაკლებ
სამუშაოს ასრულებს, ბანდლი პატარავდება, სტეკ-ტრეისები იკითხება და
თანამედროვე ბრაუზერის API-ებთან პრობლემა აღარ არსებობს.

ახალ პროექტში ამის შესახებ ფიქრი არ გჭირდებათ — უბრალოდ სთეითი
სიგნალებში შეინახეთ.
